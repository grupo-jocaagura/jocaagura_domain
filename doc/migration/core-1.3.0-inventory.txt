ACTUALIZACION POSTERIOR AL INVENTARIO
Se aprobo el breaking change de conversiones Flutter de ModelVector:
ModelVector.fromOffset(offset) -> UtilsFlutter.fromOffset(offset)
vector.offset -> UtilsFlutter.toOffset(vector)
Ambos metodos preservan dx/dy sin redondeo ni validacion. Se retiro el part local
de ModelVector y se importa/reexporta selectivamente el tipo canonico, su enum y
sus constantes. UtilsFlutter se expone desde el barrel historico.
El resto de este documento y los CSV describen el inventario previo a ese cambio;
volver a ejecutar el script genera la matriz del estado actual.
Tambien se retiro la implementacion local de Model: los modelos locales y
ModelVector ahora comparten el contrato nominal del core mediante el import y
reexport existentes. El resto de sustituciones del inventario sigue pendiente.

ADAPTACIONES OBLIGATORIAS
1. lib/jocaagura_domain.dart: retirar solo Model y defaultErrorItem locales cuando
   se adopten los canonicos; conservar barrel y parts complementarios. Model debe
   ser el MISMO tipo nominal entre core, modelos y las capas Flutter.
2. databases_crud_usecases.dart: retirar solo los 10 DTOs canonicos:
   DeleteManyParams, DeleteParams, EnsureParams, MutateParams, PatchParams,
   ReadManyParams, ReadParams, WatchParams, WriteManyParams, WriteParams.
   Conservar usecases ejecutables y adaptar su uso de esos DTOs.
3. ModelVector: core no ofrece factory fromOffset ni getter offset. El getter
   puede vivir en una extension Flutter; una extension no preserva la invocacion
   del factory ModelVector.fromOffset. Se requiere una decision explicita entre
   facade compatible y nuevo helper con migracion de consumidores. No afirmar
   identidad nominal y compatibilidad completa del constructor simultaneamente.
4. ModelMainMenuModel: el core usa ModelIconData y no tiene onPressed; domain
   usa IconData y callback. Mantener un adaptador Flutter con conversion explicita
   al dato core y resolver el nombre exportado (hide/prefijo/nombre de adaptador).
   Un reexport directo no conserva el constructor historico ni su JSON.

DIFERENCIAS DE COMPORTAMIENTO QUE REQUIEREN DECISION
- AttributeModel, PersonModel, UserModel, ModelCrudLogEntry, modelos clinicos,
  LedgerModel, grupos y LegalIdModel: revisar igualdad/hash de colecciones.
- AcceptanceClauseModel, DentalConditionModel y MedicalDiagnosisTabModel:
  core compara campos en lugar de depender solo de hashCode.
- DeathRecordModel.fromJson: core corrige la asignacion de person/address/recordId.
- LegalIdModel.fromJson: core recupera attributes antes omitidos.
- ModelAssessment: core expone parametro timeLimit; revisar constructor publico.
- Algunos decoders eliminan debugPrint; preservar datos no implica conservar logs.
Estas diferencias exceden la allowlist previa (Either/Left/Right/SDK). Deben
registrarse y aceptarse explicitamente o preservarse mediante una adaptacion
justificada. La version major por si sola no autoriza cambios semanticos extra.

LIMITES
Inventario estatico con extraccion lexical de declaraciones a nivel de archivo;
no es un informe del analyzer ni una prueba de compatibilidad de API. Los CSV
no enumeran todos los metodos/funciones globales; el diff permite revisar el codigo
restante, incluidos helpers. Igualdad normalizada no demuestra independencia del
comportamiento de dependencias. CONSERVAR significa sin equivalente nominal
detectado en core/modelos, no certificacion de que no requiera ajustes de tipos.
No se ejecutaron nuevas pruebas de migracion porque aqui no se movio codigo.
